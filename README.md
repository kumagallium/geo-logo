# geo-logo

円と直線だけでロゴを **構成的に** 設計する Web アプリ。

「完成ロゴ」と「設計図」を**同一の幾何データから**出力するのが中核です。設計図は
生成画像に後から重ねたグリッドではなく、実際にブーリアン演算へ渡された円・直線
そのものです。

```
① LLM が構成プランを DSL(JSON) で出力
       ↓
② 正規化 — 寸法をモジュール系へスナップし、幾何制約をソルバーで解く
       ↓
③ paper.js のブーリアン演算で最終パスを導出
       ↓
④ 同じデータから logo.svg と blueprint.svg を出力
```

設計判断のほとんどは**実測で決めています**。効かなかったことも残してあるので、
[実測から決めたこと](#実測から決めたこと) を読むと、この形になった理由が追えます。

## セットアップ

```bash
pnpm install
pnpm dev      # web: http://localhost:5173 / api: http://localhost:8787
```

起動したら右上のチップから **AI 設定** を開き、プロバイダーと API キーを登録します。
API キーがなくてもサンプルの閲覧・DSL 編集・SVG 書き出しは動きます。

| コマンド | 内容 |
| --- | --- |
| `pnpm dev` | Vite + Hono を同時起動 |
| `pnpm test` | ユニットテスト（Vitest） |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm build` | 型チェック＋本番ビルド |

## コマンドラインの道具

UI を通さずに、計画（JSON）から直接描いて測れます。**案は並べないと選べない**ので、
まとめて焼く道具を中心に据えています。

```bash
pnpm tsx scripts/sheet.ts tmp/sheet.png samples/*.json   # 並べて 1 枚に焼き、計測する
pnpm tsx scripts/render.ts plan.json 出力名               # 1 件を全診断つきで
pnpm tsx scripts/draft.ts plan.json 出力名                # ラフを直す（輪郭方式）
pnpm tsx scripts/steps.ts plan.json                       # どの演算で塊が壊れたか
pnpm tsx scripts/figures.ts 3 "ブリーフ"                   # 実機で生成して並べる
pnpm tsx scripts/pick.ts "題材" a.json b.json              # 視覚モデルで順位を付ける
pnpm tsx scripts/kamon-stats.ts                           # 家紋 390 点から定石を測る
pnpm draw "ブリーフ" 出力名                                # 絵を作らせて作図へ起こす
pnpm reconstruct 絵.png 出力名 [許容誤差]                  # 手元の絵から作図を起こす
```

計画 JSON の種類（design / archetype / figure / outline / emblem）は鍵の有無で
見分けるので、どの道具にもそのまま渡せます。

`samples/` に手描きの計画を置いてあります。**判定を足すときは、まずここへ当てて
「壊れていないものを咎めないか」を確かめてください。**

## 2 つの実行モード

| | サーバーモード | 静的モード |
|---|---|---|
| 使う場面 | ローカル `pnpm dev` / セルフホスト | GitHub Pages などの静的配信 |
| API キーの保管 | サーバー側 `data/models.json`（macOS は Keychain へ移行可） | ブラウザの localStorage |
| LLM 呼び出し | Hono サーバー経由 | ブラウザからプロバイダーへ直接 |
| 判定方法 | `/api/health` が JSON を返すか（`src/lib/runtime-mode.ts`） | |

設計エージェント本体（`src/lib/design-agent.ts`）はどちらのモードでも同一のコードを
使います。

## 生成の経路

題材によって効く組み立て方が違うので、経路を分けて候補ごとに割り当てています
（`modeForVariant`）。

| 経路 | モデルに書かせるもの | 効く題材 |
| --- | --- | --- |
| **画像**（`core/reconstruct.ts`） | **絵そのもの**（幾何は後から当てる） | 具象全般。構図が要るもの |
| **型**（`core/archetypes.ts`） | 9 種の型と、囲い・反復・抜きの選択 | 抽象的な主題（循環・成長・波紋） |
| **関係**（`core/figure.ts`） | 節点を「何に、どう触れて」置くか | 紋・正面の顔・放射のもの |
| **輪郭**（`core/outline.ts`） | 輪郭が通る点（ラフ） | 具象。自由な曲線が要るもの |
| **節点**（`core/emblem.ts`） | 同心の輪の重ね | 的・車輪・目のような入れ子 |

### 絵を先に作り、作図を後から当てる（画像方式）

上の 4 経路はすべて**順方向**です——モデルに幾何を書かせ、それを組み立てる。
これだと**構図と白の切り方を、モデルが幾何の言葉で決めなければならない**。
そこが届かず、出来上がりが素人の絵になります。切り分けの検査が明快でした:

| 白を全部消すと | |
| --- | --- |
| 熊の顔（輪郭方式） | **円の上に円が 2 つ**。鼠にも猫にもなる＝輪郭が何も語っていない |
| `c-sakura`（関係方式） | まだ桜と剣。輪郭が主題を担っている |

白の形も測りました。輪郭方式の熊は白 5 個のうち 4 個が丸（細長さ 1.0〜1.4）で、
**等幅のキーラインと打ち抜いた丸**しかありません。手本にした市販ツールの出力は
白が端で細り、方向を持ち、幅が場所ごとに違う——黒と同じ手間で描かれています。

順序を入れ替えます。**先に絵として作らせ、その絵から作図を起こす。**

```
① 画像モデルが二値のシルエットを描く      lib/image-agent.ts
       ↓
② 画素の隙間を辿って輪郭を取り出す        core/reconstruct.ts
       ↓
③ 円弧を当て、半径を畳み、接線を揃える    core/trace.ts（既存）
       ↓
④ 同じデータから logo.svg と blueprint.svg
```

**後半は元々ありました。** `trace.ts` は「既にある形から円弧列を復元する」ために
書かれたもので、足りていなかったのは②——画素から輪郭を取り出す一段だけです。

```bash
pnpm draw "ゴリラのように強いガラスを作る会社のロゴ" gorilla   # 生成して復元
pnpm reconstruct 絵.png out 0.012                              # 手元の絵から復元
pnpm reconstruct samples/c-sakura.json out                     # 往復検査（鍵不要）
```

**画像モデルの宛先は言語モデルと別に持ちます。** さくら AI Engine には画像生成が
ありません（`/v1/models` は 12 件すべてチャット・埋め込み・音声。VL モデルは画像を
読むだけで描けません）。`GOOGLE_GENERATIVE_AI_API_KEY` か `OPENAI_API_KEY` を
置けば宛先は自動で決まります——両方あるときは**無償枠のある Google**（AI Studio は
1 日 500 枚まで無料）を採ります。

**手元の生成器も同じ口で使えます**（鍵も課金も不要）。ローカルの拡散モデルは道具
ごとに API が違うので（Draw Things・ComfyUI・mflux で三者三様）、宛先ごとに
アダプタを書くのはやめ、**PNG を 1 枚書く**ことだけを約束させています。

```bash
uv tool install mflux
GEOLOGO_IMAGE_COMMAND="mflux-generate-z-image-turbo --steps 9 -q 8 --width {size} --height {size} --prompt-file {promptFile} --output {out}"
```

`{prompt}` `{promptFile}` `{out}` `{size}` が差し替わります。シェルは通さないので、
改行や引用符を含むプロンプトでも壊れません。FLUX schnell は Hugging Face の
ログインが要る（ゲート付き）ので、ゲートの無い Z-Image Turbo を例にしています。

**無償枠は「請求先を紐づけていないプロジェクト」の意味**なので、紐づけない限り
勝手に課金へ切り替わることはありません。使い切ると 429 が返るだけです。逆に、
すでに請求先を紐づけたプロジェクトの鍵は最初から従量課金です。`pnpm draw` は
**1 回の実行で 1 枚**しか作らないので、取り返しのつかない使い方にはなりません。

- **抽象度のレバーは許容誤差 1 つ**（`tolerance`、既定 0.012）。本数指定の口も
  ありますが、二分探索が上限まで刻もうとして冗長になり精度も落ちます。比は
  マーク全体に対して取ります——輪郭ごとに取ると小さな部品だけ細かく刻まれます
- **入れ子が正しく出ます。** 包含の深さがそのまま add / sub / add になるので、
  囲いの中に塊を置く構成が書けます。手で書く経路では抜きが必ず最後に効くため、
  これは構造的に不可能でした
- **反転して来た絵は自動で直します。** 「黒地に白抜き」で来ると、外周が紙面
  いっぱいの四角になり主題のほうが「抜き」として扱われる——静かに壊れるので、
  縁が墨で埋まっているかで判定します（家紋 corpus の 74% がこの構造でした）
- **粗さは 2 つの比で決まります。** マーク全体に対する `tolerance` だけで切ると
  小さな部品が溶けるので（マークの 1.2% は、1/10 の部品にとっては 12%）、部品
  自身に対する `detail` でも頭を抑えます

### 手元の拡散モデルで、復元できる絵が出ます

Z-Image Turbo（6B・ゲートなし・ゼロ円）に本番と同じプロンプトを投げたところ、
二値・単一マーク・背景なし・文字なしの絵が返り、**白が描かれていました**——
眉庇・鼻・口の切れ込み・眉間の皺。順方向の経路で最後まで届かなかったものが、
絵から起こすと最初から入っています。正面のゴリラ 3 案（seed 違い）で:

| | 復元の一致 | 対称度 | 覗き |
| --- | --- | --- | --- |
| seed 3 | 94.7% | 88% | 3 |
| seed 11 | 95.8% | 91% | 13 |
| seed 42 | 96.0% | 95% | 5 |

`pnpm draw` が生成 → 復元 → SVG まで通しで動きます（1 回の実行で 1 枚。
M1 Max で 1 枚 1〜2 分、初回のみ重み 31GB の取得）。

この検査で復元側の欠陥が 3 つ見つかり、直しました。

- **小さいが意味のある白を捨てていた。** ゴミ除去の閾値 0.2% で、眉間の皺
  （0.1%）と口角の切れ込み（0.04%）が消えて表情が変わっていた。本物のゴミは
  1 画素程度なので、桁を 2 つ下げても分けられる
- **対称軸を外接矩形の中央に決め打ちしていた。** 生成画像は片側の毛先が少し
  出ているだけで軸がずれ、本当は対称なマークが非対称と判定される（3 枚中 2 枚が
  中央だと 94〜96% で不合格、0.05 ずらすと 99〜100%）。中央の周りを探すようにし、
  対になる輪郭は片方だけ当てて鏡像で作る
- **1 輪郭 64 セグメントの上限で設計ごと落ちていた。** 歩くゴリラの外周は筋の
  切れ込みを含むので、誤差 0.006 で超える。はみ出した輪郭**だけ**緩めて収める

### 対称は、輪郭ではなく画素で揃える

正面のゴリラで、対称度が 88〜95% 止まりでした。原因は**画素ではほぼ対称なのに、
輪郭のつながり方（位相）が左右で違う**こと——片側だけ 1〜2 画素の橋で目が外周に
繋がっている、など。輪郭を取り出してから対称にしようとしても、位相が違うので
原理的に直りません（実測: 顔の白が軸を 4 回横切り、右側の区間に相方が無かった。
対称で穴の無い輪郭は軸をちょうど 2 回しか横切れないので、4 回は位相の非対称）。

**輪郭を取り出す前に、マスクを画素で対称化します**（`symmetrizeMask`）。軸は
中央の周りを探し、鏡像の位置の**近傍**に墨があるかで一致を数えます（厳密一致だと
本当は対称なマークが 96% 止まりで落ちる。輪郭側の判定と同じ 2% を画素に直した）。
対称なら片側をもう片側に写す。位相まで揃うので、下流は 2 回横切る輪郭だけを
扱えばよく、対称度は 3 枚とも 100% になりました。

一方で**「洗練」の差は対称だけではありません**。手本にした市販ツールのゴリラと
セグメント数を比べると:

| | 輪郭 | セグメント | 1 本あたり | 内訳 |
| --- | --- | --- | --- | --- |
| 手本 | 10 | 73 | 7.3 | ベジェ 30 / 弧 27 / 直線 15 |
| うち（tol 0.006） | 8 | 120 | 15.0 | 弧 112 / 直線 8 |

**うちは 1 本あたり倍のセグメントを使い、直線がほとんど無い。** 理由は 2 つ。
3 次ベジェが無いので同じ曲がりに弧を多く要すること、接線を揃える `smoothJoints`
が biarc で本数を倍にすること。直線が少ないのは、生成された絵そのものが丸いのと、
biarc が直線も弧の対に置き換えるため。ここは道具側の宿題です。

### 復元の忠実さは、絵の複雑さで決まります

家紋 55 点を「絵」として焼き、画素だけから復元して一致率を測りました。

| 輪郭の本数 | 件数 | 一致 平均 | 最悪 |
| --- | --- | --- | --- |
| 1〜4 | 15 | 97.6% | 95.6% |
| 5〜9 | 17 | 95.1% | 91.4% |
| 10〜19 | 13 | 93.2% | 87.3% |
| 20 以上 | 10 | 91.5% | 88.0% |

**単純なマークはほぼそのまま戻り、込み入ったものは鈍ります。** 竹に雀のような
紋（輪郭 33 本）では雀が溶けます。一致率 90% でも、輪郭の切れ味は目に見えて
落ちるので、この数字は上限であって合格点ではありません。

### 関係で組む

座標ではなく**関係**を書かせます。`on`（親の id）と `grip` で置き方を指定すると、
そのまま DSL の制約になります。

| grip | 意味 | DSL |
| --- | --- | --- |
| `outside` | 外から接する（耳・こぶ・嘴） | `tangent(external)` |
| `inside` | 内から接する（目・覗き・鼻） | `tangent(internal)` |
| `on` | 中心が相手の輪郭上（手足・花弁） | `onCircle` |
| `center` | 同心（囲い・音の輪） | `concentric` |

そのうえに 4 つの機構が乗ります。

- **入れ子** — `layers: ["ink","paper","ink"]` で環・白・瞳。演算は宣言順の逐次
- **配列** — `count` と `spread` で親の曲線に沿って n 個。親が円なら円周、弧なら弧、
  棒なら軸。肋骨・棘・羽根・音の輪がこれ 1 つで出る。`taper` で端を細らせる
- **ペン** — 図全体で 1 本の線幅。部品ごとに決めると太さが揃わない
- **白の縁取り** — `outline` で、太らせた同じ形を先に抜く。重なった部品を一定幅の
  白で分ける
- **直線の切り込み** — `blade`（平らな面）と `notch`（楔）。`layers: ["paper"]`
  にすると塊を直線で削ぎ、ink のままなら棘になる

**丸だけでは塊のままでした。** 語彙が disc / ring / arc / bar / vesica / limb と
**全部丸く**、bar は棒であって切る面ではなく、`layers` の白は同心にしか置けない。
関係をどれだけ積んでも輪郭が塊で残ります（実測: `samples/` の関係方式は墨/凸包が
64〜85%。手本にした紋章ロゴは目分量で 40〜55%）。手本の鋭さはほとんどが直線の
切り込みから来ていた——獅子の岩と鬣、犬の首、有翼馬の風切羽。`blade` / `notch` は
そのために足しました。同じ題材を組み直すと墨/凸包が 75% → 44〜53% まで下がります。

**四肢**は太さの違う 2 円を外接接線で包んで作ります（`limb`）。円と直線だけで
テーパーが出るので、自由曲線を使わずに済みます。

**方角は言葉で書けます** — `"up"` `"upleft"` `"start"` `"end"`。数でも書けますが、
角度の符号を取り違えて頭が下に付く出力が多かったため、言葉を既定にしています。

### ラフを描いて作図で整える

人がやる作図は「ラフを描いて、あとから作図線で整える」順です。この経路は
その後半（`core/trace.ts` の弧当てはめ・半径の畳み込み・接線合わせ）を使います。

モデルには 20〜45 点の**ラフ**を書かせます。円弧に均す工程が別にあるので、点を
増やしても「なぞっただけ」にはなりません。むしろ点が足りないと形が出ません。

`scripts/draft.ts` が、番号を振った点・補間した曲線・当てはめた円弧の継ぎ目・完成形
を 1 枚に重ねて出します。完成したシルエットだけを見ていると**どの点が悪いのか
分からず**、直すたびに勘で座標を動かすことになるためです。

**白の縁取り**は関係方式と同じく `keyline`（幅。モジュール）で入ります。輪郭を
書いた順に重ね、後から来た輪郭の縁に沿って白を敷きます。仕掛けも同じで、太らせた
同じ形を先に抜いてから本体を置きます。ただし太らせ方が違い、点列を太らせて当て
はめ直すのではなく**当てはめ済みの弧をそのまま等距離へ移す**（`offsetContour`）。
本数も継ぎ目の対応も変わらないので、幅が構成上どこでも一定になります。

これを入れる前は、境目ごとに細長い `hole` を手で引いていました。幅が揃わないうえ、
輪郭を直すたびに引き直すことになっていました。

## DSL

座標は **モジュール(M)** 単位。原点は構成の中心、y は下向き（SVG 準拠）、角度は
度数法で時計回り。

**プリミティブ** — `circle` / `ring` / `arc` / `bar`（太さのある直線）/ `wedge`（扇形）/
`rect` / `poly` / `contour`（円弧でできた閉じた輪郭）

**制約** — 座標を手計算する代わりに関係として宣言します。ソルバーが解きます。

| 制約 | 意味 |
| --- | --- |
| `tangent(a, b, external\|internal)` | 2 円を接する位置へ補正 |
| `concentric(a, b)` | 同心 |
| `align(ids, x\|y)` | 指定軸の座標を揃える |
| `onCircle(point, circle)` | point の中心を circle の円周上に置く |

**組み立て** — `steps` は逐次適用（`add` / `sub` / `intersect`）。`groups` が 1 段の
中間形状、`parts` が最終形状。`part.mirror: "vertical"` で左半分だけ設計して反転できます。

```jsonc
{
  "name": "Vesica Eye",
  "shapes": [
    { "kind": "circle", "id": "top",    "cx": 0, "cy": -0.809, "r": 1.618 },
    { "kind": "circle", "id": "bottom", "cx": 0, "cy":  0.809, "r": 1.618 },
    { "kind": "circle", "id": "pupil",  "cx": 0, "cy": 0, "r": 0.5, "pinned": true }
  ],
  "parts": [{
    "id": "eye",
    "steps": [
      { "op": "add",       "ref": "top" },
      { "op": "intersect", "ref": "bottom" },
      { "op": "sub",       "ref": "pupil" }
    ]
  }]
}
```

## 正規化

LLM が返す数値はそのままでは `2.87` `1.43` のように汚く、それが「幾何学的に設計
した感」を殺します。`normalize.ts` は次の順で処理します。**順序が本質的**です。

1. **半径・太さのスナップ** — φ 冪 / フィボナッチ比 / 1/2 刻みの候補集合へ最近傍
   スナップ（相対許容差 9%）。遠い値は「意図された値」として温存
2. **座標の初期スナップ** — グリッド交点へ（許容差 7%）。`pinned: true` は対象外
3. **制約の緩和解法** — 1 パスぶんの補正をまとめてから平均して適用する反復を
   240 パス（ヤコビ法）
4. **端数の再スナップ** — 全部を同じ土台に対して判定し、採否を決めてからまとめて
   適用する。「制約の総誤差が悪化しないか」を実測し、悪化するなら差し戻す

半径を先に確定してから中心を動かすのは、逆にすると接点が壊れた状態で丸められ
「ほぼ接している」ズレが残るためです。4 の差し戻しがないと、せっかく解いた接点を
グリッド丸めが壊します（実測で 0.009M のズレ）。

3 と 4 で「まとめてから適用する」形にしているのは、**順序が結果を変えないため**です。
制約を 1 つずつ即座に反映すると、左右対称に組んだ設計でも `tangent(eye, head)` が
head を動かしてから `tangent(eyeM, head)` が評価され、対が 0.0016 ずれます。

正規化の全履歴は UI の「正規化レポート」に出ます。

## 生成の検証

`lib/design-agent.ts` は生成結果を「見た目が良いか」ではなく**幾何として成立して
いるか**で機械判定し、問題があるときだけ具体的な指摘を添えて再生成します。判定が
決定的なのでリトライが無限に回りません。

- 参照 id の解決失敗 / `steps` の先頭が `add` でない
- 制約が解けていない（残差 > 1e-3）
- 塗り形状が空、または `intersect` の結果がほぼ消えている
- 完成形の縦横比が極端（12:1 超）
- 小さく離れた墨（全体の 1〜5%）がある
- インクが外接矩形の 22% 未満 / 78% 超
- 最も細い線が短辺の 1/25 未満

## 測る

「洗練された作図に見えるか」は主観ですが、そう見えるものが共通して持つ性質は
測れます。`core/metrics.ts` が返すもの:

| 指標 | 何を見るか |
| --- | --- |
| 図形 / 頂点 / 輪郭 | 規模 |
| **角** | 30° を超えて折れる頂点の数。丸い団子は 0 になる |
| 半径・線幅の種類 | 外接半径で正規化し 8% で畳む。家紋の計測と同じ土俵 |
| インク率 | 塗り面積 / 外接矩形 |
| **塊** | 塗り面積 / 墨の凸包。「ぼてっとして見える」を数にしたもの |
| 左右対称度 | 画素の鏡像一致 |
| **島** | 離れた墨の面積比。4 近傍で塗り分けて、見えているとおりに数える |
| **覗き** | 白に囲まれた墨（瞳・抜き）。島とは別に数える |

「角」を入れてあるのは、寸法の種類が少なく対称な塊は**ただの丸でも達成できる**
ためです。「覗き」を島と分けているのは、混ぜると二重丸の目が「浮いている」と
誤判定されるためです。

「塊」は角だけでは足りないので足しました。**浅い折れをいくら並べても塊は塊のまま**
で、角の数では丸い団子と articulate したマークが分かれません。凸包との差なら
「どれだけ食い込んでいるか」が直接出ます（実測: 縄 27% / ペガサス 44% に対し、
熊 77% / 魚 84% / クローバー 85%。後者が「ぼてっと」と読まれる側）。ただし
**低いほど良いという指標ではありません**——散らばった案も低く出ます。島と
並べて読んでください。

## 実測から決めたこと

### 効いたこと

| 変更 | 実測 |
| --- | --- |
| 座標ではなく**関係**を書かせる | 同じ題材で図形数が 5〜16 → 14〜36。線幅は 9 件中 8 件が 1 種 |
| **白の縁取り**（一定幅のキーライン） | 手描きの 1 例で 頂点 25 → 61、角 10 → 26 |
| ラフを **20〜45 点**にする | 点 6〜14 では輪郭ではなく落書きになり、どの題材も卵になる |
| 当てはめの許容誤差 **0.025** | 0.06 は輪郭が 3 つの円へ潰れ、0.012 は点をなぞって凸凹が残る |
| **構図の定石**を先に選ばせる | 走る四つ足が円の数珠つなぎから四肢のある横姿へ |
| **直線の切り込み**（blade / notch） | 同じ題材を組み直して墨/凸包が 75% → 44〜53% |
| 特徴の丸みは**別輪郭＋キーライン**で残す | 熊の耳を輪郭の凸で描くと角に畳まれる。別の円にすると丸が残る |

### 効かなかったこと

**縁取りを深く食い込ませて手足を繋ぎ止めること。** `grip: "on"` だけ食い込みの
補正が抜けていたので、手足に `outline` を付けると切り離されるのはそのせいだと
考えて直しました。**直っていませんでした**——縁取りは部品の全周を回るので、
どれだけ深く置いても白が一周し、島は分かれます。撤回しました。分けたい部品に
だけ付ける、が正しい使い方です。

**家紋の実測どおりのペン幅。** 家紋 390 点を測り直すと、corpus の 74% が「黒い
下敷きに白抜き」構造のため反転したまま測られており、外接半径が 1.7 倍に膨らんで
いました。直して測るとペン幅は外接半径の 0.10 / 0.17 / 0.25 で、既定の約 2 倍です。

そのまま入れたら壊れました。魚の骨の肋骨が 1 本の帯に溶け、**頂点 62 → 35 /
角 52 → 20** と articulation が半減。家紋は 5〜10 要素、こちらは 20〜40 要素あるので、
**実測の定数は要素密度ごと別物**でした。

**同心の帯を親に触れるまで縮める修復。** 浮いて見えるのを防ぐつもりでしたが、
囲い・フリル・冠羽・バンドがことごとく親に飲まれて消えました（バンドは size 2.35 →
r 2.06 になり、頭 r 2.1 からの出っぱりが 0.15 しか残らない）。**そもそも囲いは
触れていないのが正しい**——「丸に三つ葉」の丸は葉に触れていません。撤去しました。

**「大きな塊が 2 つに割れている」の判定。** 同心の弧でできたマークは弧ごとに離れて
いて、枠も入れ子になりません（5 島に分かれ、枠は x 101..152 / 86..121 / 78..107 …と
ずれて並ぶ）。「割れている」と「そう作ってある」を画素から見分ける方法が見つからず、
正しい構図を咎める害のほうが大きいと判断しました。小さなゴミだけを見ます。

### 静かに壊れていたもの

いずれも**警告を出さずに壊れる**ため、出力を見比べるまで気づけませんでした。

- **ブーリアンの向き** — paper.js は unite を重ねた CompoundPath で結果が黙って空に
  なることがある。頭に内接する小円を union した瞬間に胴・頭・四肢が消え、次の `add`
  が新しい塊として積み直すので、完成形を見ても「何か足りない」としか分からない。
  `foldSteps` に不変条件を入れた（和は面積を減らさない、差と積は増やさない）
- **合成形への制約** — ヴェシカと四肢は複数の円の合成なので、片方の円にだけ制約を
  張るとソルバーが引き剥がす。花弁 24 枚が全滅した
- **作図の順序** — 節点の解決は「親が解けたものから」なので、放っておくと兄弟が
  逆順になる。胴・白・腕 と宣言した図で白が腕を丸ごと消した。宣言順へ戻す
- **角の平均化** — `smoothJoints` が全アンカーで接線を平均しており、嘴・棘・鰭の
  切れ込みが必ず丸まっていた。折れ角 55° 超は角として残す
- **縁取りの共食い** — 反復した個体が互いの縁取りで削り合う。花弁 5 枚を 340° に
  詰めると島が 1 → 6、角が 5 → 20 になり楔形の屑が残る。節点の中では抜きを全部
  先に済ませてから置く

### 閾値の決め方

閾値は「解像度や畳み込みの設定に追随していないか」を確かめてから採用しています。

- **島の下限 1%** — 96 / 192 / 384 / 768 px で数えると、1% 未満の島だけが解像度に
  追随して増えた（ある生成物で 2 → 5 → 5 → 9）。1% 以上はどの解像度でも同じ数
- **半径の「種類数」は載せない** — 畳み込み閾値をそのまま反映するだけの数字なので、
  `kamon-stats.ts` は閾値に依らない検定（対数半径の自己相関）を併記する

### 構造化出力は有効にしない方が良い

OpenAI 互換の `response_format: json_schema` を有効にすると**設計の質が落ちました**。
同一プロンプト各 5 回:

| | 警告なし | 一発成功 | 総試行 |
|---|---|---|---|
| 構造化出力 ON | 2/5 | 2/5 | 11 |
| 構造化出力 OFF | 5/5 | 5/5 | 5 |

制約付きデコードは JSON の「形」は保証しますが、この DSL のように参照整合性
（`steps.ref` が実在 id を指す）が要る構造では、形に合わせるために意味の通らない値を
埋めてしまいます。形の担保はスキーマ検証＋修復リトライに任せ、意味はプロンプトで
作らせるほうが結果が良い、というのが実測の結論です。既定は OFF。

プロバイダーによってはスキーマ自体を拒みます（union 型の欄数の上限、複雑さの上限）。
その場合はテキストで受けて緩いスキーマで検証する経路へ切り替わります。

### 古典的な作図法をパイプラインに組み込む

Twitter の鳥（2012）・Apple・Google の G といった幾何ロゴに共通する原理を、
プロンプトと機械判定の両方に入れています。

1. **すべての曲率は円から来る** — 輪郭の曲がった部分は必ずどこかの円の弧
2. **円同士は必ず関係を持つ** — 接する／中心が相手の円周上／同心。数値を手計算せず
   制約で宣言し、ソルバーに解かせる
3. **union で塊を作り sub で食い込ませる** — 少ない要素で強い形が出る
4. **輪郭は一続きの閉じた形** — 離れて浮いた部品の寄せ集めにしない

4 番はプロンプトだけでは守られないので機械判定を入れました（`build()` の
`unrelated`）。宣言も辺に数えるのは、同心の帯のように**重ならないが正しい**構成を
誤検出しないためです。

これに合わせて `arc`（円弧の帯）プリミティブを追加しました。円弧は `ring ∩ wedge` で
書けますが、2 段の合成が必要だと DSL 上のコストが直線より高くなり、モデルは常に
直線を選びます。追加前は全出力が直線の寄せ集めでした。

### 効いたプロンプト改善

1. **完全な JSON の実例を 1 つ載せる** — 抽象的な仕様説明だけでは `steps` の構造を
   外す
2. **参照の規則を明示** — 「意味を表す名前を ref に書かない。実在する id を一字一句
   そのまま書く」。これが最頻の失敗だった
3. **構図の作法を書く** — 「外形でクリップする」「棒をはみ出したまま残さない」
4. **完成例ではなく骨組みを選ばせる** — 手本と同じ題材だけがうまくいく状態だったので、
   完成例を増やすのではなく骨組み（`pose`）の一覧から選ばせる形にした

## セキュリティ

このアプリは **API キーを保持し、ワンクリックで課金リクエストを発行する**ので、
そこを起点に設計しています。

### 静的モードでキーを保存しない理由

`<user>.github.io` は、**その利用者のすべての Pages プロジェクトでオリジンが共通**です。
localStorage はオリジン単位なので、同じアカウントの別リポジトリのページからも読めます。

そのため既定では **API キーを保存しません**（タブを閉じるまでのメモリ保持）。
保存は設定画面のチェックボックスで明示的に選ぶ形にし、「保存済みキーを localStorage
から削除」する導線も置いています。サーバーモードならキーはブラウザに一切載りません。

### LLM 出力を信頼境界として扱う

生成された SVG は `dangerouslySetInnerHTML` でページへ注入されます。つまり
**LLM の出力が markup に到達する**ため、ここが最大の攻撃面です。実際、初期実装には
`palette` が任意文字列で `fill="${...}"` に補間される注入経路がありました
（`src/core/security.test.ts` に再現テストがあります）。

対策は 3 層:

1. **スキーマで形を限定**（`src/core/dsl.ts`）— 色は 16 進表記のみ、id は
   `[A-Za-z0-9_-]` のみ、座標・寸法は有限かつ範囲内、配列は要素数上限つき
2. **レンダラでエスケープ**（`src/core/render.ts`）— 色は再検証して不正なら黒へ落とし、
   属性値は `& " ' < >` をエスケープ
3. **CSP `script-src 'self'`** — インライン script も `onload=` 等のイベント属性も禁止。
   1・2 が破られても実行されない

数値の範囲制限は DoS 対策も兼ねています（`r: 1e9` でソルバーが発散し、巨大な SVG で
ブラウザが固まるのを防ぐ）。

### プロバイダーをまたいで設定を共有しない

`GEOLOGO_BASE_URL` は openai-compatible 用の設定で、anthropic では読みません。
別プロバイダーの URL を `.env` に残したままプロバイダーを切り替えると、**キーが
その別プロバイダーのエンドポイントへ送られる**ためです。Anthropic の宛先を変える
ときは SDK と同じ `ANTHROPIC_BASE_URL` を使います。

### ローカル API サーバー

`pnpm dev` のサーバーは API キーを持つので、利用者が開いている**無関係なサイト**から
叩かれないようにしています。

- **CORS を張らない** — ブラウザからは Vite の proxy 経由で同一オリジンとして届くので
  不要。開けると任意のサイトから叩けるようになる
- **送信元を検査**（`src/server/security.ts`）— `Sec-Fetch-Site` が same-origin / none
  以外なら拒否。CORS を開けていなくても、単純リクエストは*レスポンスが読めないだけで
  副作用は発生する*ため、これが実際の CSRF 対策になる
- **`127.0.0.1` にのみバインド** — 既定の `0.0.0.0` だと同一 LAN の他端末から叩ける
- **`data/` は 0700、`models.json` は 0600** — Keychain 無効時はこのファイルがキーの実体
- `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Cache-Control: no-store`

外部ホストから使う場合は `GEOLOGO_ALLOWED_ORIGINS` で明示します。

### 配信側

- **CSP** を本番ビルドにのみ meta で注入（`vite.config.ts`）。dev に入れると HMR が
  壊れるため build 限定
- `frame-ancestors` は meta では仕様上無視されるので、**埋め込み検出は実行時**に行う
  （`src/main.tsx`）。GitHub Pages は HTTP ヘッダーを設定できないため
- `referrer: no-referrer`
- **GitHub Actions はタグではなく commit SHA で固定**。タグは可変で、上書きされると
  デプロイ成果物へ任意コードを混ぜられる。更新は Dependabot が PR で提案する
- CI は `pnpm install --frozen-lockfile --ignore-scripts`（依存の postinstall を走らせない）
- ワークフローの `permissions` は既定 `{}` で、ジョブ単位に最小権限を付与

### 残っている制約

- **静的モードでキーを「保存する」と選んだ場合**、同一オリジンの他 Pages から読めます。
  ブラウザのオリジンモデル上 `*.github.io` では回避できません。恒久的に安全にしたい
  場合は独自ドメインで配信するか、サーバーモードを使ってください
- `connect-src` はプロバイダーのエンドポイントがユーザー設定である以上 `https:` までしか
  絞れません。XSS が実行された場合の送信先制限としては弱く、実質的な防御は
  `script-src 'self'` です
- 静的モードでは API キーがブラウザからプロバイダーへ直接送られます（中継しない設計上
  必然）

```
main へ merge  →  tagpr がリリース PR を作る（version と CHANGELOG を書き換え）
                     ↓ merge
                  タグ vX.Y.Z  →  Desktop Build が起動  →  Release に .dmg / .app.tar.gz
                                                          latest.json（自動更新の案内）
```

- **tagpr**（`.tagpr` / `tagpr.yml`）が `package.json` と `tauri.conf.json` の version を
  同時に書き換えます。片方だけだと表示バージョンがずれる（Graphium で実害）
- **Desktop Build**（`desktop-build.yml`）は macOS Apple Silicon を組み、updater 用の
  `.app.tar.gz` に署名して `latest.json` を Release と Pages（`public/updater/`）の
  両方へ置きます。署名が取れなければ **latest.json を出さずに落ちます**——壊れた
  案内を配らないため
- **自動更新**（`src/lib/updater.ts`）は起動時と 24 時間ごとに `latest.json` を見て、
  新しければ画面上部に「再起動して更新」を出します。設定画面の「このアプリに
  ついて」から手でも確認できます。ブラウザ版では何もしません

Apple の署名と公証は repo の secrets（`APPLE_*` 6 つ）が揃っていれば
`tauri-action` が行います。無ければ署名なしで組みます（Gatekeeper の警告は出るが
動く）。updater の鍵は `TAURI_SIGNING_PRIVATE_KEY`。**秘密鍵を失うと以後の更新に
署名できず、配布済みのアプリが更新されなくなります**——`~/.tauri/geo-logo.key` を
別の場所にも控えてください。

## GitHub Pages

`main` への push で `.github/workflows/deploy.yml` がビルドして Pages へデプロイします。

- リポジトリ設定 → Pages → Source を **GitHub Actions** にしてください
- ワークフローが `GEOLOGO_BASE=/<repo>/` を渡すので `vite.config.ts` の `base` が合います
- Pages にはサーバーが無いため、アプリは自動的に静的モードで動きます

## 既知の制約

- **具象の語彙に穴があります。** 自由な曲線（関係方式から `contour` を出せない）と、
  直線だけで構成された面が書けません。円と接線では届かない題材があります
- **輪郭方式に一定幅のキーラインがありません。** 関係方式にはあります
- **局所的な対称は正規化で動きます。** 全体が対称な設計は保たれますが、横向きの
  題材の「親を軸にした対」（目の柄など）は、全体の対称性ではないのでソルバーが
  保つ理由を持ちません
- **Keychain 保存（`GEOLOGO_USE_KEYCHAIN=1`）は未検証です。** 実行すると利用者の
  ログインキーチェーンに書き込むため。コードは Graphium からの逐語移植です
- **視覚モデルでの採点は判別しません。** 焼いた 29 枚を 8 通りの聞き方で 443 回
  試したところ、0〜10 の採点は 29 枚中 27 枚が同じ点でした。2 枚を並べて選ばせる
  形なら 92%（正解既知の 13 組で 26 回中 24 回）当たるので、`scripts/pick.ts` は
  順位付けだけに使っています
