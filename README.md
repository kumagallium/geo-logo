# geo-logo

円と直線だけでロゴを **構成的に** 設計する Web アプリ。

「完成ロゴ」と「設計図」を**同一の幾何データから**出力するのが中核。設計図は生成画像に後から重ねたグリッドではなく、実際にブーリアン演算に使われた円・直線そのものです。

```
① LLM が構成プランを DSL(JSON) で出力
       ↓
② 正規化 — 寸法をモジュール系へスナップし、幾何制約をソルバーで解く   ← ここが肝
       ↓
③ paper.js のブーリアン演算で最終パスを導出
       ↓
④ 同じデータから logo.svg と blueprint.svg を出力
```

## 2 つの実行モード

| | サーバーモード | 静的モード |
|---|---|---|
| 使う場面 | ローカル `pnpm dev` / セルフホスト | GitHub Pages などの静的配信 |
| API キーの保管 | サーバー側 `data/models.json`（macOS は Keychain へ移行可） | ブラウザの localStorage |
| LLM 呼び出し | Hono サーバー経由 | ブラウザからプロバイダーへ直接 |
| 判定方法 | `/api/health` が JSON を返すか（`src/lib/runtime-mode.ts`） | |

Graphium の `ServerMode: "node" | "vercel"` と同じ考え方です。設計エージェント本体
（`src/lib/design-agent.ts`）はどちらのモードでも同一のコードを使います。

## セキュリティ

このアプリは **API キーを保持し、ワンクリックで課金リクエストを発行する**ので、
そこを起点に設計しています。

### 静的モードでキーを保存しない理由

`<user>.github.io` は、**その利用者のすべての Pages プロジェクトでオリジンが共通**です。
localStorage はオリジン単位なので、同じアカウントの別リポジトリのページからも読めます。

そのため既定では **API キーを保存しません**（タブを閉じるまでのメモリ保持）。
保存は設定画面のチェックボックスで明示的に選ぶ形にし、「保存済みキーを localStorage
から削除」する導線も置いています。サーバーモードならキーはブラウザに一切載りません。

### LLM 出力を信頼境界として扱う

生成された SVG は `dangerouslySetInnerHTML` でページへ注入されます。つまり
**LLM の出力が markup に到達する**ため、ここが最大の攻撃面です。実際、初期実装には
`palette` が任意文字列で `fill="${...}"` に補間される注入経路がありました
（`src/core/security.test.ts` に再現テストがあります）。

対策は 3 層:

1. **スキーマで形を限定**（`src/core/dsl.ts`）— 色は 16 進表記のみ、id は
   `[A-Za-z0-9_-]` のみ、座標・寸法は有限かつ範囲内、配列は要素数上限つき
2. **レンダラでエスケープ**（`src/core/render.ts`）— 色は再検証して不正なら黒へ落とし、
   属性値は `& " ' < >` をエスケープ
3. **CSP `script-src 'self'`** — インライン script も `onload=` 等のイベント属性も禁止。
   1・2 が破られても実行されない

数値の範囲制限は DoS 対策も兼ねています（`r: 1e9` でソルバーが発散し、
巨大な SVG でブラウザが固まるのを防ぐ）。

### ローカル API サーバー

`pnpm dev` のサーバーは API キーを持つので、利用者が開いている**無関係なサイト**から
叩かれないようにしています。

- **CORS を張らない** — ブラウザからは Vite の proxy 経由で同一オリジンとして届くので不要。
  開けると任意のサイトから叩けるようになる
- **送信元を検査**（`src/server/security.ts`）— `Sec-Fetch-Site` が same-origin / none
  以外なら拒否。CORS を開けていなくても、単純リクエストは*レスポンスが読めないだけで
  副作用は発生する*ため、これが実際の CSRF 対策になる
- **`127.0.0.1` にのみバインド** — 既定の `0.0.0.0` だと同一 LAN の他端末から叩ける
- **`data/` は 0700、`models.json` は 0600** — Keychain 無効時はこのファイルが
  キーの実体になる
- `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Cache-Control: no-store`

外部ホストから使う場合は `GEOLOGO_ALLOWED_ORIGINS` で明示します。

### 配信側

- **CSP** を本番ビルドにのみ meta で注入（`vite.config.ts`）。dev に入れると HMR が
  壊れるため build 限定
- `frame-ancestors` は meta では仕様上無視されるので、**埋め込み検出は実行時**に行う
  （`src/main.tsx`）。GitHub Pages は HTTP ヘッダーを設定できないため
- `referrer: no-referrer`
- **GitHub Actions はタグではなく commit SHA で固定**。タグは可変で、上書きされると
  デプロイ成果物へ任意コードを混ぜられる。更新は Dependabot が PR で提案する
- CI は `pnpm install --frozen-lockfile --ignore-scripts`（依存の postinstall を走らせない）
- ワークフローの `permissions` は既定 `{}` で、ジョブ単位に最小権限を付与

### 残っている制約

- **静的モードでキーを「保存する」と選んだ場合**、同一オリジンの他 Pages から読めます。
  これはブラウザのオリジンモデル上、`*.github.io` では回避できません。恒久的に安全に
  したい場合は独自ドメインで配信するか、サーバーモードを使ってください
- `connect-src` はプロバイダーのエンドポイントがユーザー設定である以上 `https:` までしか
  絞れません。XSS が実行された場合の送信先制限としては弱く、実質的な防御は
  `script-src 'self'` です
- 静的モードでは API キーがブラウザからプロバイダーへ直接送られます（中継しない設計上必然）

## GitHub Pages

`main` への push で `.github/workflows/deploy.yml` がビルドして Pages へデプロイします。

- リポジトリ設定 → Pages → Source を **GitHub Actions** にしてください
- ワークフローが `GEOLOGO_BASE=/<repo>/` を渡すので、`vite.config.ts` の `base` が自動で合います
- Pages にはサーバーが無いため、アプリは自動的に静的モードで動きます
- 無料プランで Pages を使う場合、リポジトリは public である必要があります

## AI 設定（Graphium からの移植）

Graphium の AI 設定サブシステムを移植しています。

| Graphium | geo-logo | 内容 |
|---|---|---|
| `server/config/keychain.ts` | 同左 | macOS Keychain への API キー保存（`GEOLOGO_USE_KEYCHAIN=1`） |
| `server/config/models.ts` | 同左 | `models.json` 永続化、旧形式からの Keychain 移行、キー欠落検出 |
| `server/services/llm.ts` | `lib/create-model.ts` + `lib/provider-models.ts` | プロバイダー生成とモデル一覧取得。ブラウザ実行を追加 |
| `server/services/header-model.ts` | `server/config/resolve-model.ts` | `X-LLM-API-Key` ヘッダーからのモデル解決 |
| `server/routes/models.ts` | 同左 | モデル CRUD ＋ `POST /available` |
| `lib/ai-error-codes.ts` / `lib/ai-error.ts` | 同左 | `CodedError` と表示文言への変換 |
| `lib/model-pricing.ts` | 同左 | 既知モデルの参考価格（Claude の現行世代を追記） |
| `features/settings/store.ts` | 同左 | localStorage のモデルレジストリ |
| 設定モーダルの AI タブ | `features/settings/SettingsModal.tsx` | UI は geo-logo の CSS で書き直し |

移植していないもの:

- **copilot-subscription** — `@github/copilot-sdk` とローカル CLI の subprocess 起動が必要で、
  静的配信では原理的に動かないため
- **claude-subscription** — Anthropic の規約で撤去済み（Graphium 側でも purge 対象）
- **MCP / embedding / grounding / 使用量ダッシュボード** — geo-logo に対応機能がないため

Graphium からの意図的な差分:

- `POST /api/models` で `source_model_id` を指定したとき、provider も参照元から引く。
  Graphium は `body.provider` をそのまま使い、クライアントが詰め直す前提だった
- `design-agent.ts` を `server/` から `lib/` へ移し、`LanguageModel` を引数で受け取る形にした
  （ブラウザからも同じ実装を使うため）

## DSL

座標は **モジュール(M)** 単位。原点は構成の中心、y は下向き（SVG 準拠）、角度は度数法で時計回り。

**プリミティブ** — `circle` / `ring` / `bar`（太さのある直線）/ `wedge`（扇形）/ `rect` / `poly`

**制約** — 座標を手計算する代わりに関係として宣言する。ソルバーが解きます。

| 制約 | 意味 |
| --- | --- |
| `tangent(a, b, external\|internal)` | 2 円を接する位置へ補正 |
| `concentric(a, b)` | 同心 |
| `align(ids, x\|y)` | 指定軸の座標を揃える |
| `onCircle(point, circle)` | point の中心を circle の円周上に置く |

**組み立て** — `steps` は逐次適用（`add` / `sub` / `intersect`）。`groups` が 1 段の中間形状、
`parts` が最終形状。`part.mirror: "vertical"` で左半分だけ設計して反転できます。

```jsonc
{
  "name": "Vesica Eye",
  "shapes": [
    { "kind": "circle", "id": "top",    "cx": 0, "cy": -0.809, "r": 1.618 },
    { "kind": "circle", "id": "bottom", "cx": 0, "cy":  0.809, "r": 1.618 },
    { "kind": "circle", "id": "pupil",  "cx": 0, "cy": 0, "r": 0.5, "pinned": true }
  ],
  "parts": [{
    "id": "eye",
    "steps": [
      { "op": "add",       "ref": "top" },
      { "op": "intersect", "ref": "bottom" },
      { "op": "sub",       "ref": "pupil" }
    ]
  }]
}
```

## 関係で組む（figure）

具象の題材（動物・道具・骨格）のための経路。**座標を書かせず、関係を書かせる。**

### なぜ足したか

部品方式（`core/composition.ts`）で「ヘッドホンをしたパンダ」を手で丁寧に書き、
そのまま通してみたところ、修復の各工程が設計そのものを上書きしました。

| 工程 | 何が起きたか |
| --- | --- |
| `snapToLadder` | 拡大方向にしか寄せないので、頭:胴 = 1.29 が 1.00 に潰れた |
| `enforceHierarchy` | 同率のときソート順で主役を選び、胴を頭より大きくした（2.35 → 3.80） |
| `repairVisibility` | 「目の環」を x = -0.90 から -1.87 へ押し出したが、対の「目の白」(cut) は動かなかった |

3 番目が本質です。部品は平らな配列で、「この白はこの環の内側」という関係が
存在しないので、修復が片方だけ動かせてしまう。**関係が無いものは、壊さずに
直すことができません。**

### 4 つの機構

- **関係で置く** — `on`（親の id）と `grip`。`outside` 外接 / `inside` 内接 /
  `on` 中心が親の輪郭上 / `center` 同心。置き方がそのまま DSL の
  `tangent` / `onCircle` / `concentric` になります。具象を扱う経路が
  constraints を 1 つも出していなかったのが、ここで初めて出ます
- **入れ子** — `layers: ["ink","paper","ink"]` で環・白・瞳。演算は宣言順の
  逐次にしました。部品方式は「塗りを全部足してから抜く」順に並べ替えるので、
  白が瞳を消して入れ子が作れません
- **配列** — `count` と `spread` で、親の曲線に沿って n 個。親が円なら円周、
  弧なら弧、棒なら軸に沿います。肋骨・棘・羽根・音の輪がこれ 1 つで出ます。
  `taper` で端を細らせます
- **ペン** — 図全体で 1 本。部品方式は線幅を部品の `size` から引いていたので、
  大きい部品と小さい部品で太さが変わりました

`mirror` は関係ごと反転します（鏡像側の子は鏡像側の親に付く）。

### ブーリアンの向きを検定する

パンダを組んでいて、`add nose`（頭に**内接**する小円）の union で結果が空に
なりました。paper.js が unite を重ねた CompoundPath で起こす既知の不整合です。

厄介なのは壊れ方で、そこまでに積んだ胴・頭・四肢が丸ごと消え、次の `add` が
新しい塊として積み直すため、**完成形を見ても「何か足りない」としか分かりません**。
実際、目とヘッドホンだけのマークが出ました。

`build.ts` の `foldSteps` に**演算の向き**を入れました。和は面積を減らさない、
差と積は増やさない。破ったらパスデータから作り直して 1 度やり直し、それでも
破るならその演算だけ飛ばして警告を出します。全経路に効きます。

どの演算で壊れたかは `pnpm tsx scripts/steps.ts plan.json` で 1 行ずつ見えます。

### 手本に似ているかで質が決まっていた

6 題材 × 3 案を焼いて並べたところ、**プロンプトの手本と同じ題材だけが
うまくいっていました**。魚の骨と梟（手本そのもの）は 3 案とも読めるマークに
なり、走るオオカミ・灯台・クローバーは崩れました。モデルは構成しているのでは
なく、手本を写していたことになります。

手本を増やしても題材は無限にあるので、**完成例ではなく骨組みだけの一覧**
（`pose`）を持たせ、モデルにはまず選ばせる形にしました。

| pose | 骨組み |
| --- | --- |
| `face` | 胴 →（up）頭 →（upleft）耳 →（inside）目 →（down）口 |
| `profile` | 胴 →（upleft）頭 →（downleft）前肢 →（downright）後肢 →（right）尾 |
| `skeleton` | 背骨 arc →（inside, count）肋骨 →（start）頭 →（end）尾 |
| `perched` | 台 bar →（up）胴 →（up）頭 →（down）脚 |
| `tower` | 基部 →（up）軸 →（up）頭部 →（center, count）光の弧 |
| `radial` | 芯 →（on, count, spread 360）花弁を等配置 |

選ばせた 4 題材で pose の選択は 12/12 正しく（狼 → profile、灯台 → tower、
クローバー → radial、パンダ → face）、**走る四つ足は円の数珠つなぎから
四肢のある横姿へ変わりました**。灯台とクローバーはまだ崩れます。

反復まわりも 2 つ直しました。

- **全周は刻みを 1 つ増やす** — `spread: 360, count: 3` と書かれると、
  -180 と +180 が重なって 2 箇所にしか出ていませんでした
- **混み合ったら軌道を外へ** — 芯 0.4 に葉 1.6 を 3 枚乗せると、三つ葉ではなく
  ただの丸になります。隣どうしの間隔が半径の 1.6 倍を切るなら軌道を広げます

### 参照 5 点を手で書き起こす

目標にしたい水準の紋章ロゴを 5 点、いまの語彙で 1 枚ずつ手描きして、どこまで
届くかを実測しました。**届かなかった主因の 3 つは能力不足ではなく、直前に
入れたバグ**でした。
しかも 3 つとも警告を出さずに静かに壊れます。

| バグ | 症状 |
| --- | --- |
| 合成形（vesica / limb）に制約を張るとソルバーが引き剥がす | 花弁 24 枚が全滅。片方の円だけが親へ引き寄せられ、2 円が離れて交差が空になる |
| `grip: center` の早期 return が「散らす反復」を飲み込む | 縄の撚り 24 本が全部芯に重なる |
| 混み合いの逃がし方が一律だった | 向日葵は花弁が離れて別の島、三つ葉は芯に埋まって丸 |

3 つ目は、子と親のどちらが主役かで逃がし方を変えて直しました。
子が親より大きければ軌道を外へ広げ（三つ葉・桜）、小さければ縮める（向日葵）。

残った壁は語彙の穴で、**紋と具象で必要なものが違います**。

| 壁 | どこで出たか | 状態 |
| --- | --- | --- |
| ヴェシカの細長さが 1.38:1 固定 | 花弁が豆になる（実物は 4:1） | 直した（`slender`） |
| `count` 上限 24 | 向日葵は 26 枚 | 直した（32 へ） |
| 直線の面が無い | ジャッカルの横顔が丸い塊に（参照は円弧ゼロ） | 未 |
| `bar` の太さがペン固定 | 剣の刀身に白筋を入れると刀身ごと消える | 未 |
| 反復要素を傾けられない | 縄が撚れない | 未 |
| 自由な輪郭を figure から出せない（DSL には `contour` がある） | 蛇の S 字、馬の首 | 未 |
| 輪が組み合わない（交互の重なり） | 桜の二輪 | 未 |

紋の 3 枚（向日葵・桜・縄の輪）は上の 2 つを直した時点で構造が一致しました。
具象の 2 枚（ペガサス・ジャッカル）は、円と接線の語彙では原理的に届きません。

### 効かなかったこと

**家紋の実測どおりのペン幅**。家紋 390 点を測り直すと、corpus の 74% が
「黒い下敷きに白抜き」構造のため反転したまま測られており、外接半径が 1.7 倍に
膨らんでいました。直して測るとペン幅は外接半径の 0.10 / 0.17 / 0.25 で、
既定（0.055 / 0.085 / 0.13）の約 2 倍です。

そのまま入れたら壊れました。魚の骨の肋骨が 1 本の帯に溶け、トリケラトプスの
棘が消え、**頂点 62 → 35 / 角 52 → 20** と articulation が半減しました。

家紋は 5〜10 要素、こちらは 20〜40 要素あります。ペンをマーク全体の外接半径に
対して決める以上、要素が増えれば同じ比では太すぎる。**実測の定数は要素密度ごと
別物で、そのまま移せません。**

### 実測

同じ 3 題材（パンダ / トリケラトプスの骨格 / インコと音の輪）を 3 案ずつ。

| | 図形数 | 線幅の種類 |
| --- | --- | --- |
| 部品方式 | 5〜16 | 1〜2 |
| 関係方式（gpt-oss-120b） | 15〜31 | 1〜2 |
| 関係方式（gemma-4-31B-it、手本 2 を足した後） | 14〜36 | 8/9 が 1 種 |
| 関係方式（四肢・方角の言葉を足した後） | 19〜43 | 7/9 が 1 種 |

効いたプロンプト改善:

1. **骨格の手本を足す** — 反復する棒を円の外へ放射させると、どんな題材も
   ウニになりました。「背骨を arc で 1 本引き、その弧に沿って `grip: "inside"`
   で並べる」手本を入れたら消えました
2. **波紋は arc で** — `ring`（全周）にすると主役を包んでしまい、
   何のマークか分からなくなります

コード側の修復:

- 親より大きい子を `outside` で付けると 1 点でしか触れず、宙に浮いた別の
  塊に見えます（実測: 頭の上に大きな環が浮いた）。`on`（中心を親の輪郭に
  乗せる）へ倒すと深く重なって 1 つの塊になります

### 墨が離れているかを画素で数える

「浮いた部品」は目で見て最も分かりやすい破綻なのに、機械判定がありませんでした。
`build.ts` の `unrelated` は**設計として関係が宣言されているか**を見るので、
宣言してさえいれば通ります。ところが外接は 1 点でしか触れないので、宣言があっても
目には別の物体に見えます。

`core/metrics.ts` の `islandsOf` は、出来上がった画素を 4 近傍で塗り分けて
**見えているとおりに**数えます。白に囲まれた墨（瞳・覗き）は縁から届かないので、
浮いた島とは別に `nests` として数えます。これを混ぜると、二重丸の目が
「浮いている」と誤判定されます（実際にされました）。

閾値は実測で決めました。96 / 192 / 384 / 768 px で数えると、**1% 未満の島だけが
解像度に追随して増えます**（ある生成物で 2 → 5 → 5 → 9）。輪郭が毛ほどの幅で
くびれているだけで、目には繋がっています。1% 以上の島はどの解像度でも同じ数でした。

離れていること自体は失敗ではありません。音の輪・光線・星は離して置くのが正しい。
そこで大きさで 3 つに分けて、両端だけを咎めます。

| 島の大きさ | 扱い |
| --- | --- |
| 1% 未満 | 数えない（解像度由来） |
| 1〜5% | ゴミ。指摘する |
| 5〜15% | 添え。通す（音の輪が実測 5 / 6 / 7 / 9% でここに入った） |
| 15% 以上 | マークが 2 つに割れている。指摘する |

あわせて、外接・内接で**線 1 本ぶん食い込ませる**ようにしました（`figure.ts` の
`BITE`）。幾何としての接は 1 点なので、弧や棒に接する部品が離れたまま残ります
（実測: 食い込ませないと、鳥と骨格で 4% ほどの島が 1 つずつ切り離された）。

### 演算の順は宣言順でなければならない

節点の座標は「親が解けたものから」順不同に求まります。ところがブーリアンの
順序までその順に積んでいたため、**同じ深さの兄弟が逆順**になっていました。

胴・白・腕 の順に宣言した図で、実際に出た steps は `add:body add:arm sub:gap`。
後から来た白が腕を丸ごと消し、胴に白いスリットだけが残りました。層（`layers`）
の中では逐次になっていたので気づきにくく、**節点をまたいだ入れ子だけが
成立していなかった**ことになります。

座標は解決順のまま、演算の順だけを宣言順へ戻しました。

### 囲いは触れていなくてよい

一度、同心の環・弧を「親に触れるまで縮める」修復を入れました。浮いて見える
のを防ぐつもりでしたが、**囲い・フリル・冠羽・ヘッドホンのバンドがことごとく
親に飲まれて消えました**（実測: バンドは size 2.35 → r 2.06 になり、頭 r 2.1
からの出っぱりが 0.15 しか残らない。size を 1.0/1.3/2.0/3.0 と振っても
出力は 0.79 で一定）。

そもそも囲いは触れていないのが正しい——家紋の「丸に三つ葉」の丸は葉に
触れていません。修復は撤去しました。

同じ理由で「大きな塊が 2 つに割れている」の判定も落としました。同心の弧で
できたマークは弧ごとに離れていて、枠も入れ子になりません（実測: 5 島に分かれ、
枠は x 101..152 / 86..121 / 78..107 …とずれて並ぶ）。「割れている」と
「そう作ってある」を画素から見分ける方法が見つからず、正しい構図を咎める側の
害が大きいと判断しました。**小さなゴミだけを見ます。**

### 判定の速さ

`islandsOf` は paper の `contains` を画素ごとに呼ぶので、192 px で 1 回 64 ms
かかります。これを `diagnose` に入れたところ、アーキタイプの総当たり
（4374 通り）が 280 秒延びました。

- 解像度を 96 px へ（1% 以上の島は 96〜768 px で数が変わらないことを実測済み）
- 輪郭が 1 本なら島は 1 つしかありえないので、画素を数える前に返す

で 64 ms → 16 ms になりました。

### 白の縁取り（キーライン）

洗練された紋章ロゴを何点か並べて見ると、**例外なく持っている操作**が 1 つ
あります。重なった部品の境目が、どこも同じ太さの白で分かれていること——
翼と胴、首と胸、顎と頬、花弁と円板。これが無いと部品が黒い塊へ溶けます。

`layers` の白は同心にしか置けず、幅も半径に比例してばらつく（同じ図の中で
2.2 倍ちがう）ので、重なりを分ける用には使えません。節点ごとの `outline`
（ペン幅の何倍か）を足し、**太らせた同じ形を先に抜いてから本体を置く**形で
実装しました。演算が宣言順になっている前提の仕組みです。

手書きの 1 例で 頂点 25 → 61 / 角 10 → 26。パラメータ 1 つで articulation が
倍以上になります。

縁取りは部品の全周を回るので、外へ突き出した部品に付けるとその部品が本体から
切り離されます（幾何としては正しい。紋章の翼は実際に離して描かれます）。
接している部品には、縁取りのぶんだけ深く食い込ませるようにしました。

### 四肢は外接接線で包む

一定の太さの棒では、腕も脚も尾も同じ太さの線になります。太さの違う 2 円を
外接接線で包むと、円と直線だけでテーパーが出ます——古典的な作図そのもので、
自由曲線を使わずに済みます。`figure.ts` の `limb` がこれで、`length`（付け根の
半径の何倍の長さか）と `tip`（先端の太さの比）で形が決まります。

### 方角は言葉で書かせる

`at` を数だけにしていたとき、「頭は胴の上」を +90 と書いて頭が下に付く出力が
繰り返し出ました。y が下向きだと知らないと書けないからです。
`"up"` `"down"` `"upleft"` … と書けるようにし、鏡像では左右の語を入れ替えます。
弧や棒を親にしたときは `"start"` `"middle"` `"end"` として読みます。
数でも書けるので、細かく詰めたいときは従来どおりです。

### 角を消さない

`smoothJoints` は継ぎ目の接線を揃えて輪郭を流れさせる機構ですが、**全アンカーを
例外なく平均していました**。嘴・棘・鰭・尾の切れ込みは、輪郭がそこで折れること
そのものが形の手がかりなので、これを消すと題材が読めない塊になります。

手本の「泳ぐ魚」（プロンプトに載っている座標）を通すと、尾の切れ込みが消えて
卵になり、目の抜きまで演算が破綻していました。折れ角が 55° を超えるアンカーは
意図された角と見なして平均しない、という例外を入れた結果:

| | 角 | 輪郭 | 目の抜き |
| --- | --- | --- | --- |
| 全部平均（従来） | 0 | 1 本 | 破綻して消えた |
| 角を残す | 5 | 3 本 | 出る |

### 下絵の縁と、本物の欠け

生成物が「全体的にギザギザしている」ように見えたので切り分けたところ、
**2 つの別々の話**が混ざっていました。

**階段状の縁は道具のせい。** `rasterize` は画素ごとに内外を判定するだけで、
アンチエイリアスをしていませんでした。240px の下絵では縁が階段になり、
案を並べて見比べるときに「作図が汚い」と読み違えます（実際に読み違えた）。
960px にすると消え、本物の SVG では最初から出ません。**製品の出力はベクタ
なので実害はありません。** 見るための絵だけ 3×3 の標本で均すようにしました。
島を数える二値の判定は 1 標本のまま（1 回 16ms を上げたくない）。

**欠けと屑は本物でした。** 原因は縁取りで、**反復した個体どうしが互いの
縁取りで削り合っていました**。花弁 5 枚を 340° に詰めて縁取りを付けると、
島が 1 → 6、角が 5 → 20 になり、楔形の屑が残ります。

縁取りは「下にあるものから分ける」ためのもので、自分の兄弟を切ってはいけない。
節点の中では抜きを全部先に済ませてから置くようにしました（島 6 → 2）。

## ラフを描いて作図で整える（輪郭方式）

人がやる作図は「ラフを描いて、あとから作図線で整える」順です。geo-logo は
**後半を最初から持っていました**——`trace.ts` の弧当てはめ・半径の畳み込み・
接線合わせがそれです。足りていなかったのは前半でした。

輪郭方式は弱いモデル向けに「点 6〜14」しか要求しておらず、それは輪郭ではなく
落書きです。上限を点 64 / 輪郭 12 へ上げ、プロンプトを「20〜45 点のラフ」に
変えました。**円弧に均す工程が別にあるので、点を増やしても「なぞっただけ」に
はなりません。**

Opus 5 にラフを描かせると、輪郭 5 本・点 53 で鋭いジャッカルの横顔が出ました。
**関係で円を組む経路では原理的に届かない形**です（参照も円弧を 1 つも
使っていない）。紋には関係方式、具象にはラフ方式、という住み分けになります。

### 角を残したまま滑らかに繋ぐ

閉じた曲線として一気に補間すると、描いた側が意図した角も均されます
（ジャッカルの立った耳 2 本が 1 つの丸い瘤に溶けた）。制御点を二重にする定石は
中心化パラメータだと点間距離が 0 になって壊れるので（魚の尾が消えた）、
**角で切って区間ごとに開いた曲線として補間**します。

### 当てはめの許容誤差

0.06 は「点 6〜14」向けの値で、密なラフには緩すぎました。熊とジャッカルの
両方に 0.06 / 0.025 / 0.012 を当てて比べています。

| 許容誤差 | 結果 |
| --- | --- |
| 0.06 | 輪郭が 3 つの円へ潰れる。耳も口吻も消える |
| **0.025** | 口吻・耳・目・キーラインが揃う。魚の二叉の尾も戻る |
| 0.012 | 点をなぞって凸凹が残る |

さらに、点が増えるほど描いた側の意図は細かくなるので、基準の点数（14）からの
比で緩めます。呼ぶ側が決めたいときは `polish` で上書きできます。

### 下描き用紙

```bash
pnpm tsx scripts/draft.ts samples/bear-sketch.json bear
```

完成したシルエットだけを見ていると、**どの点が悪いのか分からない**。直すたびに
勘で座標を動かすことになります。モデルが目隠しなのと同じことを、書く側も
していました。番号を振った点・補間した曲線・当てはめた円弧の継ぎ目・完成形を
1 枚に重ねて出します（SVG なのでラスタライザを増やさない）。

上の許容誤差の問題も、この道具で「点 25 が弧 6 本に畳まれている」と見えた
ところから分かりました。

### 測る道具

「洗練された作図に見えるか」は主観ですが、そう見えるものが共通して持つ性質は
測れます。`core/metrics.ts` が図形数・頂点数・**角**（30° を超えて折れる頂点）・
輪郭数・半径と線幅の種類・インク率・左右対称度を返します。角を入れてあるのは、
寸法の種類が少なく対称な塊は**ただの丸でも達成できる**ためです。丸い団子は
角が 0 になります。

案は並べないと選べないので、まとめて 1 枚に焼く道具を置いてあります。

```bash
pnpm tsx scripts/sheet.ts tmp/sheet.png plan1.json plan2.json   # 並べて計測
pnpm tsx scripts/render.ts plan.json 出力名                      # 1 件を全診断つきで
pnpm tsx scripts/steps.ts plan.json                              # どの演算で壊れたか
pnpm tsx scripts/draft.ts plan.json 出力名                       # ラフを直す（輪郭方式）
pnpm tsx scripts/figures.ts 3 "ブリーフ"                          # 実機で生成して並べる
pnpm tsx scripts/pick.ts "題材" a.json b.json                     # 視覚モデルで順位を付ける
pnpm tsx scripts/pairs.ts                                        # 左右の対が動いていないか
```

`samples/` に手描きの計画を置いてあります。**判定を足すときは、まずここへ
当てて「壊れていないものを咎めないか」を確かめてください。** 島の判定は
これで 2 度直しました。詳細は `samples/README.md`。

計画 JSON の種類（design / composition / outline / emblem / archetype / figure）は
鍵の有無で見分けるので、どの道具にもそのまま渡せます。

## 正規化（② — なぜこれが要るのか）

LLM が返す数値はそのままでは `2.87` `1.43` のように汚く、それが「幾何学的に設計した感」を
殺します。`normalize.ts` は次の順で処理します。**順序が本質的**です。

1. **半径・太さのスナップ** — φ 冪 / フィボナッチ比 / 1/2 刻みの候補集合へ最近傍スナップ
   （相対許容差 9%）。遠い値は「意図された値」として温存
2. **座標の初期スナップ** — グリッド交点へ（許容差 7%）。`pinned: true` は対象外
3. **制約の緩和解法** — 違反量の半分ずつ両側を寄せる反復を 240 パス
   （Position Based Dynamics 相当）
4. **端数の再スナップ** — ただし 1 シェイプずつ「制約の総誤差が悪化しないか」を実測し、
   悪化するなら差し戻す

半径を先に確定してから中心を動かすのは、逆にすると接点が壊れた状態で丸められ
「ほぼ接している」ズレが残るためです。4 の差し戻しがないと、せっかく解いた接点を
グリッド丸めが壊します（実測で 0.009M のズレが出ました）。

正規化の全履歴は UI の「正規化レポート」に出ます。

## 生成の検証（①のリトライ）

`lib/design-agent.ts` は生成結果を「見た目が良いか」ではなく
**幾何として成立しているか**で機械判定します。

- 参照 id の解決失敗 / `steps` の先頭が `add` でない
- 制約が解けていない（残差 > 1e-3）
- 塗り形状が空、または `intersect` の結果がほぼ消えている
- 完成形の縦横比が極端（12:1 超）

問題が出た場合のみ、具体的な指摘を添えて 1 度だけ再生成します。判定が決定的なので
リトライが無限に回りません。

## 実測メモ（さくら AI Engine / gpt-oss-120b）

`pnpm smoke "<ブリーフ>"` で 1 件生成し、パイプライン全体を通せます。

### 構造化出力は有効にしない方が良い

OpenAI 互換の `response_format: json_schema` は、さくら側が `pattern` まで含めて
正しく強制します。しかし**有効にすると設計の質が落ちました**。同一プロンプト各 5 回:

| | 警告なし | 一発成功 | 総試行 |
|---|---|---|---|
| 構造化出力 ON | 2/5 | 2/5 | 11 |
| 構造化出力 OFF | 5/5 | 5/5 | 5 |

制約付きデコードは JSON の「形」は保証しますが、この DSL のように参照整合性
（`steps.ref` が実在 id を指す）が要る構造では、形に合わせるために意味の通らない値を
埋めてしまいます。形の担保はスキーマ検証＋修復リトライに任せ、意味はプロンプトで
作らせる方が結果が良い、というのが実測の結論です。既定は OFF。
モデルによっては逆転しうるので `structuredOutputs` / `GEOLOGO_STRUCTURED_OUTPUTS` で
切り替えられます。

### 古典的な作図法をパイプラインに組み込む

Twitter の鳥（2012）・Apple・Google の G といった幾何ロゴを分析すると、
共通する 4 つの原理が出てきます。これをプロンプトと機械判定の両方に入れています。

1. **すべての曲率は円から来る** — 輪郭の曲がった部分は必ずどこかの円の弧。
   自由曲線は使わない。だから拡大しても半径が説明できる
2. **円同士は必ず関係を持つ** — 接する（tangent）／中心が相手の円周上（onCircle、
   ヴェシカ）／同心（concentric）。数値を手計算せず制約で宣言し、ソルバーに解かせる
3. **union で塊を作り sub で食い込ませる** — Apple の「かじり跡」型。
   少ない要素で強い形が出る
4. **輪郭は一続きの閉じた形** — 離れて浮いた部品の寄せ集めにしない

4 番は最も守られにくく、プロンプトだけでは不十分だったので機械判定を入れました
（`build()` の `unrelated`）。「実際に重なっている」か「constraints で関係が宣言
されている」かでグラフを作り、非連結なら孤立要素として指摘して再生成させます。
宣言も辺に数えるのは、同心の帯のように**重ならないが正しい**構成を誤検出しないためです
（手描きサンプル 4 件すべてで誤検出ゼロを確認）。

これに合わせて `arc`（円弧の帯）プリミティブを追加しました。円弧は `ring ∩ wedge` で
書けますが、2 段の合成が必要だと DSL 上のコストが直線より高くなり、モデルは常に
直線を選んでしまいます。実際、追加前は全出力が直線の寄せ集めでした。

### 効いたプロンプト改善

1. **完全な JSON の実例を 1 つ載せる** — 抽象的な仕様説明だけでは `steps` の構造を
   外していました
2. **参照の規則を明示** — 「"mountain" のような意味を表す名前を ref に書かない。
   実在する id を一字一句そのまま書く」。これが最頻の失敗でした
3. **構図の作法を書く** — 「外形でクリップする」「棒をはみ出したまま残さない」。
   これを入れる前は要素が円から突き出した寄せ集めになり、入れた後は 3/3 で
   `intersect` を使うようになりました

### 検出を追加した失敗

「基準円を add → 要素を add → 同じ基準円で intersect」をやると、結果が基準円
そのものに戻ります。幾何としては正常（面積も縦横比も妥当）なので他の判定を
素通りしますが、出力はただの黒い円です。`build()` が対称差でこれを検出します
（面積と外形寸法の比較では足りません。リングの切り欠きと横棒が相殺して
一致する例が実際にありました）。

  ログインキーチェーンに書き込むため。コードは Graphium からの逐語移植です
- **Anthropic / OpenAI / Google プロバイダー経由の生成は未実行**です（さくら AI Engine

- 生成される構図が「三角の稜線＋下の横棒」に収束しがちで、**多様性は乏しい**です。
  円弧の使い方（`wedge` / `ring`）を引き出すプロンプトはまだ調整の余地があります
